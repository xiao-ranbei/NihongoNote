## 一、规划原则

1. **先拆后加**：`App.tsx` 已由 S0 拆出 8 个模块（1763 → 937 行），但 `App()` 本体仍约 865 行、承载全部状态逻辑。把本体拆成 hooks 是流式与范围标注的共同前置。
2. **每一档都可独立验证、可独立回滚**：每个工作项结束后应用都能正常启动与使用。
3. **成本纪律高于功能速度**：LLM-011 是硬约束，规划中任何 AI 实测都必须先取得用户许可；能被本地验证的（离线断言、本地 Ollama）优先。
4. **不做过度工程**：单人自用项目，不为「未来可能的多用户/公网」预留复杂度（详见技术栈选型的「刻意不引入清单」）。
5. **量化优先**：每个里程碑给出可测量的指标，而不是「体验更好」这类判断。
6. **工作量用级别标注（S/M/L/XL）而非天数**：单人业余节奏下天数估算无参考价值，级别用于排序与拆分。

| 级别 | 含义 |
| --- | --- |
| S | 单点改动，半天内可完成并验证 |
| M | 需要改 2-4 个模块，需要一轮自检 |
| L | 跨层改动（契约 + 服务端 + 前端），需要多轮验证 |
| XL | 需要先拆分或先定契约，风险高，必须分步交付 |

## 四、里程碑详解

### M1 实时反馈

**目标**：把「点了开始 → 等几分钟 → 突然出全部结果」变成「逐段出现、随时可停」。

| # | 工作项 | 需求 ID | 级别 | 交付物 |
| --- | --- | --- | --- | --- |
| M1.1 | 继续拆分 `App.tsx` 本体（S0 已完成第一轮：1763 → 937 行，8 个模块） | MAINT-002 | L | 把 `App()` 本体的状态逻辑拆为 `useAnalysis` / `useLibrary` / `useSettings` / `useTheme`，组件层保持纯展示 |
| M1.2 | 段级流式上屏（SSE） | STREAM-001/002/004/005 | L | 服务端事件流 + 前端 `streamAnalysis()` + 逐段合并 |
| M1.3 | 闭合对象扫描器 | STREAM-002 | M | `json-stream-scanner.ts` + 离线断言 |
| M1.4 | 空闲超时与错误可见 | STREAM-003 | S | 上游空闲阈值 + 先推错误再中止 |
| M1.5 | 引入 vitest | MAINT-003 | M | 测试框架 + 关键路径用例迁移 |
| M1.6 | 请求指标与终态事件 | OBS-001/002/003/PRIV-004 | M | 本地 JSONL 事件 + `first_segment_ms` / `duration_ms` / `error_category` |
| M1.7 | token 边界逐项对齐修复 | QUAL-001 | S | 校验从「一处不符即失败」改为「逐项对齐，仅补不丢」 |
| M1.8 | 增量上屏的布局平滑 | PERF-002 | S | 新段淡入 + 高度过渡（CSS，无新依赖） |
| M1.9 | 最小块保护（防小尾巴） | —（借鉴项，无对应需求 ID） | S | `planBatches` 增加最小块合并：尾批过短时并入前一批（受预算上限约束），避免固定开销被浪费 |
| M1.10 | provider 输出估算钩子（离线标定） | —（实现项） | M | 由 provider 声明自己的输出估算，替代按 DeepSeek 标定的通用式；后端提供从 `usage_json` 拟合系数的离线脚本（纯本地、零 LLM） |

**量化指标**
- 首段反馈 `first_segment_ms` 从「整篇结束」降到「单段耗时量级」（本地 9B 场景目标 < 90s，DeepSeek 场景 < 30s）；
- 流式过程中**零**「未通过校验的内容上屏」；
- 取消后已完成段 100% 保留、未完成段 100% 可续跑；
- 事件日志记录率：每次分析恰好 1 条终态事件；
- 装箱效率（M1.9）：不再出现「单独成批且该批估算成本低于预算 30%」的尾批，除非全篇只有一批或并入会超预算；
- 装箱准确度（M1.10）：本地模型不再恒定 1 段/批，批次数随段落数下降（具体阈值以标定后的系数确定）；
- **成本预估可信**：确定性分批——同一篇文章 + 同一套配置，重复预览得到完全相同的预估（不因运行时状态变化）。

**验证方式**
- 离线：`pnpm typecheck` + `verify`（断言扩展到流式扫描器、边界对齐与最小块合并）；vitest 覆盖 `json-stream-scanner`、`segment-preparation`、`llm-budget`；
- 本地实测（零云端费用）：用本机 Ollama 跑一篇 20+ 段文章，观察逐段上屏、取消、续跑、事件日志；
- 云端实测：**需用户明确许可**（LLM-011），仅在本地验证通过后进行。

**完成标准（DoD）**
1. 拆分的 hooks 各自职责单一，`App.tsx` 降到 500 行以内（S0 后为 937 行，其中 `App()` 本体约 865 行）；
2. 本地 Ollama 端到端：逐段上屏可见、取消与续跑正确、事件日志完整；
3. `pnpm typecheck` 全绿、`verify` 断言数不低于现基线且新项通过；
4. 半截 JSON 不渲染（有对应用例或手工验证记录）；
5. `planBatches` 最小块保护有专属断言：① 尾批过短时并入前一批；② 并入后超预算则不并；③ 单段本身超预算仍单独成批（防死循环）；④ 分批结果**确定性**（同输入必得同输出）。

**风险与缓解**
- 重构回归（XL 项）：先补 vitest 用例再动结构；每拆一个 hook 就完整验证一次阅读流程；
- 流式与整批两套校验逻辑漂移：**强制复用同一份校验/合并函数**（架构文档不变量 2）；
- M1.9 的合并可能把批次做大到接近上限：并入前必须用同一预算校验，宁可保留小尾批也不越界。

**回滚方案**
- M1.1：拆分按 hook 逐个提交，任一步出问题即回退该步；旧的单文件版本保留在 Git 历史；
- M1.2：流式通道以**新增端点**形式引入，旧端点保持可用；出问题时不订阅流、退回轮询，功能不受影响；
- M1.7：对齐修复实现为独立函数，异常时回退到原「严格相等」判定；
- M1.9：最小块合并实现为 `planBatches` 内的独立分支，回滚即恢复原逐段装箱逻辑（不影响其他调用方）。

| M2.3 | `CanonicalAnalysis` / `LevelExplanation` 拆分 | LLM-002b/c | XL | 契约分层 + 等级切换只重生成解释层 |
| M2.4 | 语气证据与礼貌五档 | LLM-002b/002c | S | `toneEvidence` + 五档枚举 |
| M2.5 | 锚点换位与移动端抽屉 | DOC-011、UX | M | 视口边缘换位 + 窄屏底部抽屉 |
| M2.6 | 词性归一 | QUAL-003 | S | `normalizePos()` + 分组配色 |
| M2.7 | 上下文裁剪 | CTX-001 | S | 长文上下文收敛 + token 前缀定位 |
| M2.8 | 宽松 JSON 兜底 | QUAL-002 | S | 严格失败后按字段边界截取 |

**量化指标**
- 范围渲染：重叠范围零嵌套可点击元素（DOM 结构检查）；重复词点击命中正确率 100%；
- 等级切换：切换 N5→N1 不触发重新分词、不产生新的基础事实请求（token 用量为 0）；
- 上下文裁剪后长文 prompt 体积下降（对比记录）。

**验证方式**：离线断言（区间切分、层级循环、等级切换不触达 provider）+ 手工验收（用固定评估样本的可视结果比对）。

**完成标准（DoD）**
1. 语法/语气范围在阅读框中正确渲染，四层循环行为符合需求；
2. 切换等级只重生成解释层，`CanonicalAnalysis` 不变；
3. 历史数据向后兼容（旧 `SegmentAnalysis` 仍可读）。

**风险与缓解**
- M2.3 是契约级变更，风险最高：**先写契约与迁移方案，再动实现**；旧数据通过 `schemaVersion` 兼容读取；
- 范围渲染的性能：先用区间扫描生成不重叠片段，避免逐 token DOM 计算。

**回滚方案**：M2.3 拆分为「新增字段并存 → 双读 → 切换写入」三步，任一步可停；M2.1 渲染在新组件内实现，出问题可退回纯 token 渲染。

## 八、明确不排期

无限并发、公网部署、注册登录、多设备同步、图片/OCR/PDF、任意网页抓取、学习积分与社交、第二套分词权威、把等级混入事实层。

**理由**：与「单人本机、成本可控、定位可靠」的架构不变式冲突，或真实收益未经验证。
