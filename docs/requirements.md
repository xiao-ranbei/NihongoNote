# 产品需求说明

**版本**：0.2
**日期**：2026-08-27
**范围**：个人本地 Web 应用

## 一、已确认的需求

| 项目 | 决策 |
| --- | --- |
| 使用对象 | 只给自己使用 |
| 部署方式 | 本机启动的本地 Web 应用 |
| 输入 | 直接粘贴日语文章或对话文本 |
| 内容长度 | 希望支持整篇长文，可接受更长等待 |
| 分析范围 | 词汇/活用、助词/语法、句意、语气态度、礼貌程度、潜台词、上下文和接话理由都需要 |
| 阅读交互 | 句子级高亮；词语悬浮或点击看词汇/助词/语法；点击句子看整句和语气 |
| 对话角色 | 用户可使用 A/B 或角色名；AI 自动识别并允许修改 |
| 日语水平 | 希望覆盖初级到高级，可按文章选择难度 |
| 朗读 | 自然、标准的东京式日语；第一版允许一个默认音色 |
| 朗读扩展 | 后续支持多人不同音色和语气 |
| 跟读 | 第一版录音、保存、回放，不承诺自动发音评分 |
| 数据 | 保存文章、解析、音频和录音，并支持历史搜索 |
| 云服务 | 可以发送到第三方模型/TTS，优先质量和开发速度 |
| 首个 LLM 候选 | DeepSeek |
| 首个 LLM 协议 | DeepSeek OpenAI-compatible API |
| 后续 LLM 协议 | Anthropic-compatible API，作为可插拔的第二适配器 |
| 账号 | 第一版没有 API 账号，按推荐方案接入 |
| 时间 | 没有硬性期限，优先方案扎实和可长期使用 |

## 二、LLM 服务接入需求

### 已确认的接入策略

1. P1 首先接入 DeepSeek 的 OpenAI-compatible API。
2. 内部统一使用 NihongoNote 自己的 `LlmProvider` 接口和版本化 JSON schema。
3. Anthropic-compatible API 需要保留接入能力，但不阻塞第一条可用分析链路。
4. 前端不直接请求任何 LLM 服务；API key、base URL、模型和协议只由本机 API 管理。
5. DeepSeek 只负责文本分析；朗读和录音使用独立的 TTS/浏览器能力。

DeepSeek 官方入口：

- OpenAI-compatible：`https://api.deepseek.com`
- Anthropic-compatible：`https://api.deepseek.com/anthropic`

具体模型名称、限流规则和价格在实施时以[官方文档](https://api-docs.deepseek.com/)为准。

### LLM 功能需求

| ID | 需求 | 验收标准 |
| --- | --- | --- |
| LLM-001 | 配置 LLM provider | 可在本机服务端配置 provider、protocol、base URL、model 和 API key；密钥不出现在前端 |
| LLM-002 | DeepSeek 首条链路 | 使用 DeepSeek OpenAI-compatible API 完成一段真实日语材料的分析 |
| LLM-003 | 结构化 JSON | 请求启用 JSON 输出，结果通过本地 schema 校验后才可保存 |
| LLM-004 | 原文绑定 | 模型返回的 segment/token ID 必须来自服务端输入，不能由前端用字符串搜索猜测 |
| LLM-005 | 空结果和截断处理 | 空内容、非法 JSON 或长度截断必须标记为失败并可重试，不得显示为完成 |
| LLM-006 | 协议可替换 | 增加 Anthropic-compatible adapter 时，不修改前端阅读器和持久化分析 schema |
| LLM-007 | 调用元数据 | 保存 provider、model、protocol、promptVersion、输入/输出用量、缓存命中和错误分类 |

DeepSeek JSON Output 需要在 prompt 中明确要求 JSON，并设置合理的 `max_tokens`；即使返回合法 JSON，也必须继续校验业务字段和原文 ID。

当前实现已覆盖 LLM-001、LLM-003、LLM-004、LLM-005 的基础链路，以及 DeepSeek OpenAI-compatible adapter；LLM-002 仍需使用真实 DeepSeek API key 和评估样本完成质量/费用验收。LLM-006（Anthropic-compatible adapter）属于后续阶段。

## 三、产品目标

### 目标

让学习者在不离开原文的情况下，理解“这句话是什么、为什么这样说、说话人是什么态度、下一句为什么这样接”，并立即听到自然日语，再进行跟读。

### 非目标

第一版不包含：

- 公网注册、登录、多人协作或计费；
- 自动抓取任意网页；
- OCR、图片/PDF 识别；
- 自动发音评分、音高曲线诊断或实时纠音；
- 以 Agent 对话窗口替代文章阅读器；
- 保证模型解释等同于语言学教材或人工教师结论。

## 四、核心用户流程

1. 打开本机 Web 应用。
2. 粘贴文章或对话，选择标题、学习难度和可选的角色标记。
3. 点击“开始分析”，看到分段进度。
4. 在原文阅读：
   - 悬浮/点击词语，查看词形、原形、读音、词性、词义、活用和在本句中的作用；
   - 点击助词，查看它在本句中的语法功能；
   - 点击句子，查看中文意思、语法结构、说话人态度、礼貌程度、潜台词和上下文；
   - 对话中查看“上一句为何导致这一句回复”。
5. 点击句子或段落播放日语朗读。
6. 点击录音，完成跟读后保存并回听。
7. 从历史列表搜索文章，继续复习。

## 五、功能需求

### 4.1 文档和文章阅读

| ID | 需求 | 验收标准 |
| --- | --- | --- |
| DOC-001 | 粘贴日语文章或对话 | 粘贴后保留换行、标点和原文顺序，并可在分析前编辑 |
| DOC-002 | 识别句子和段落 | 一篇内容被拆成稳定的段落/句子 ID，后续解析和音频都引用这些 ID |
| DOC-003 | 显示分析进度 | 长文分析时显示已完成、进行中、失败和待处理段落 |
| DOC-004 | 句子级高亮 | 鼠标移入或点击句子时有明确的选中状态，弹窗/侧栏不会遮挡原文 |
| DOC-005 | 长文断点续跑 | 单段失败只重试该段；关闭页面后再次打开仍能查看已完成部分 |
| DOC-006 | 历史搜索 | 按标题、原文片段和创建时间搜索已保存文章 |

### 4.2 词语、助词和语法分析

每个可交互词语至少应能显示：

- 原文表面形；
- 原形/词典形；
- 假名读音；
- 词性；
- 中文释义；
- 活用前后形态（若适用）；
- 在当前句子中的具体作用；
- 不确定时的候选解释或置信提示。

助词和语法解释至少应能显示：

- 语法点名称；
- 本句中的连接方式；
- 本句中的功能和语义；
- 为什么不是常见的其他用法；
- 一句简短的替换/对比例句（模型能可靠生成时）。

### 4.3 句子、语气和对话分析

每个句子至少应能显示：

- 自然中文意思；
- 句子结构和关键语法；
- 说话人的态度：如陈述、请求、拒绝、强调、试探、缓和、强硬等；
- 礼貌程度和语气强弱；
- 省略、潜台词或上下文依赖；
- 如果是对话：上一句如何影响本句、本句为何采用这种回复；
- 对存在多种合理解释的内容明确标记不确定性。

模型输出必须包含原文句子 ID，前端不得依赖模型返回的字符串位置自行猜测绑定关系。
token 的边界、ID、surface 和字符偏移由本机服务生成并传给模型；模型返回的 token 必须逐项匹配本地边界。

### 4.4 对话角色

- 支持用户输入 `A:`、`B:` 或任意角色名。
- 未标注时，AI 可以推断角色，但必须允许用户修改。
- 角色修改后，相关句子的朗读和态度展示应使用更新后的角色。
- 第一版不要求根据年龄、性别或社会关系自动推断复杂设定；这些信息可作为可选备注。

### 4.5 朗读和跟读

| ID | 需求 | 验收标准 |
| --- | --- | --- |
| AUDIO-001 | 标准日语朗读 | 生成自然、清晰的东京式日语，默认一个音色 |
| AUDIO-002 | 保留停顿和标点 | 句号、逗号、换行和对话轮次产生合理停顿 |
| AUDIO-003 | 逐句/段落播放 | 用户可从当前句开始播放，不必每次重生成整篇 |
| AUDIO-004 | 录音 | 浏览器请求麦克风权限后可录制当前句或段落 |
| AUDIO-005 | 保存和回听 | 录音关联文章和句子，可在历史文章中重新播放 |
| AUDIO-006 | 录音失败提示 | 用户拒绝权限、设备不可用或格式不支持时显示明确原因 |
| AUDIO-007 | 音色扩展预留 | 数据模型保存 provider、voice、角色和语气参数，后续可支持多人音色 |

第一版不把“标准语气”解释为自动生成完美的戏剧化情绪。默认目标是自然、清晰、标准；角色音色和强弱语气是后续扩展。

### 4.6 数据管理

- 新建、重命名和删除文章。
- 删除文章时可选择同时删除关联音频和录音。
- 保存分析提示词/解析协议版本，避免模型升级后无法追踪结果来源。
- 支持导出原文、解析 JSON 和录音文件，作为后续备份能力；若首版时间有限，导出可排在历史搜索之后。

## 六、建议的数据结构

```text
Document
  id, title, sourceText, targetLevel, createdAt, updatedAt

Segment
  id, documentId, index, text, speaker, status
  translation, grammarSummary, tone, politeness
  impliedMeaning, replyReason, contextNote

TokenAnalysis
  id, segmentId, start, end, surface, lemma, reading
  partOfSpeech, conjugation, gloss, particleFunction
  grammarPoint, explanation, confidence

AudioAsset
  id, segmentId, provider, voice, format, path
  speed, ssmlVersion, createdAt

Recording
  id, segmentId, mimeType, path, durationMs, createdAt
```

`start` 和 `end` 应由服务端分词结果生成，并以稳定的 Unicode 字符偏移保存。前端不能只依赖视觉上的字符串搜索，以免重复词语绑定到错误位置。

## 七、非功能需求

### 可靠性

- 每个分析段落有独立状态：`queued`、`processing`、`completed`、`failed`。
- 网络错误、限流和模型结构化输出失败必须对用户可见。
- 重试要有次数上限和退避，不得无限重试或静默返回空结果。
- 只有通过 schema 校验的结果才能写入完成状态。

### 隐私和安全

- 服务只监听本机地址，第一版不暴露公网。
- LLM/TTS API 密钥只存在服务端环境变量，不发送到浏览器。
- 默认日志不记录完整文章、API 密钥或录音内容。
- 用户可以单独删除文章、云端生成的音频和本地录音。
- 使用麦克风前明确请求浏览器权限。

### 可维护性

- AI、TTS、分词器都通过适配器隔离。
- 当前 token 边界可使用 Node `Intl.Segmenter`，后续可替换为更精细的日语形态素分析器而不改变前端绑定协议。
- LLM 协议通过 adapter 隔离；业务层不得依赖 OpenAI 或 Anthropic 的响应对象。
- 分析输出使用版本化 JSON schema。
- 前端渲染层不直接拼接模型 Markdown 作为结构化数据源。

## 八、验收样例

准备至少三类真实材料：

1. 一段包含多个助词和活用的普通文章；
2. 一段包含省略、委婉表达和上下文依赖的双人对话；
3. 一篇超过单次模型上下文舒适范围的长文。

每类材料都应通过以下检查：

- 原文顺序、换行和标点不丢失；
- 词语和句子定位稳定；
- 解析能指出具体原文证据；
- 长文失败可单段重试；
- 音频能逐句播放；
- 录音保存后重新打开文章仍可回听；
- API 出错时显示原因，而不是伪装成“分析完成”。
- 使用 DeepSeek OpenAI-compatible API 时，结构化结果能够通过 schema 校验并绑定到正确句段。
- 将 provider 配置为未实现的协议时，服务启动或请求失败必须给出明确提示，不能静默切换到其他模型。
